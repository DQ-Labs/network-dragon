# Linux / Proxmox deployment candidate

Deployment is **not yet validated**. Docker and a Linux VM were unavailable in the implementation workspace. The Compose worker intentionally has no raw-network capabilities and requires explicit selection via `--profile worker`. Do not treat the candidate as a finished ARP-scanning deployment.

Obtain the authorized IPv4 CIDR (up to 256 addresses), on-link interface, VM CPU/RAM/disk, management hostname, trusted proxy source IPs, and TLS approach before enabling a live scope. Start with the plan's provisional Debian VM sizing (2 vCPU, 2 GB RAM, 16–24 GB disk); measure actual load. Never alter the Proxmox host's networking to make this application work.

1. Copy `deploy/config.example.toml` to a private path on the VM. Keep scanning and notifications false. Create no live network yet.
2. Resolve and record base-image digests and the deployed application image digest. The Dockerfile's tag defaults are build candidates, not reproducibly pinned production artifacts. Lock the Debian package snapshot/Nmap version as part of the validated release.
3. Set `NETWORK_DRAGON_CONFIG_FILE` to that private TOML and build the image. Initialize the data volume with `docker compose -f deploy/compose.yaml run --rm web init`, then run `... web create-admin` interactively. The image prepares UID/GID 10001; verify named-volume ownership and write access.
4. Start web only. It binds the VM's loopback port 8000. Configure the trusted reverse proxy to forward Host and X-Forwarded-Proto, terminate HTTPS, and restrict management access. Set `trusted_proxy_ips` to its actual source IP(s), never a wildcard. Keep `allow_http_local=false`.
5. Validate discovery privileges in an isolated, expressly authorized lab first. The runner requires interface up-state, an on-link IPv4 address, and a direct route through the configured interface. It uses `-sn -PR --send-eth --privileged`; unprivileged degraded discovery is not silently substituted. Validate the smallest Nmap-specific capability arrangement and record it. No `privileged: true`, Docker socket, host PID namespace, blanket sudo, capabilities on Python, or host-network `net.*` sysctls are acceptable shortcuts. The sample deliberately does not claim a working capability recipe.
6. Once validated, set the installation CIDR/interface allowlists, enable `live_scanning`, create a matching live network through Settings, and start the worker profile. Initial scanning remains in baseline review. Keep delivery false during the pilot.
7. Review identities and watch fixed devices. Validate presence with an actual controlled outage, ARP behavior, DHCP changes, service churn, and scanner-interface failure. Verify that device detail explains stale/offline/filtered evidence correctly.
8. Mount Pushover application/user secrets using permission-restricted files and `PUSHOVER_TOKEN_FILE` / `PUSHOVER_USER_FILE` in both service environments; do not place values in Compose, the database, Git, or browser requests. Environment values are also supported for local controlled use. Configure delivery, explicitly click **Send test notification**, review its sanitized result, then finish baseline review and resume future delivery. No test message is sent on startup.

Both processes share one local filesystem data volume. SMB/NFS live databases are unsupported. The worker uses host networking, exposes no HTTP listener, and inherits bounded temporary storage/process/log settings. The web service drops all capabilities. Verify read-only application filesystem behavior, image wheel packaging, data permissions, crash restart, and the singleton lease on Linux.

Firewall acceptance must test HTTPS access from authorized management sources, denial of new VLAN-initiated connections to protected networks, and only intended outbound Pushover HTTPS/DNS/time/update access. Include IPv6 firewall policy despite IPv4-only scanning. These checks need the actual deployment network and cannot be inferred from application tests.
